Every AWS lab teaches you the clicks. Very few explain the decisions behind them.
I recently worked through the *Configure an Amazon S3 bucket* lab, and the steps are
straightforward: create a bucket, make it public, upload a few files, turn on static
website hosting. Ten minutes, done.

But the same walkthrough has a few sharp edges. The bucket policy in the lab is
overly broad, the public-access toggles are easy to misread, and the website
endpoint gives you plain HTTP. If you copy the lab into a real project, those
details matter.

Here is the full walkthrough, with the reasoning filled in.

## What S3 actually gives you

An S3 bucket is object storage, not a web server. Each object can be up to 5 TB,
there is no cap on total storage, and every object gets an HTTP URL. That is enough
to serve HTML, CSS, images, and PDFs to a browser.

What it does not give you:

- Server-side code (no PHP, no Node, no redirects based on logic)
- Authentication or per-user access
- HTTPS on the static website endpoint
- A custom domain without extra services
- Edge caching by default

For a brochure site, a docs page, or a demo, none of that is a problem. For anything
with a login or an API, S3 alone is the wrong tool.

## Create the bucket

The lab uses **US East (Ohio)**, or `us-east-2`. Pick a region close to your users
and stay consistent, because the bucket's region determines both the object URL and
the website endpoint. You cannot move a bucket to another region later without
recreating it.

| Setting | Lab value | Why it matters |
| --- | --- | --- |
| Region | US East (Ohio) | Sets the endpoint; cannot be changed later |
| Bucket name | `s3-59676255` | Must be globally unique and DNS-compatible |
| Object Ownership | ACLs enabled | Required for the lab's "Make public using ACL" step |
| Bucket Versioning | Enabled | Recovery and audit trail; optional for a static site |

Steps:

1. In the AWS console, set the region selector to **US East (Ohio)**.
2. Open **All services → Storage → S3**, then choose **Create bucket**.
3. Enter a unique bucket name, keep the region, and select **ACLs enabled** under
   Object Ownership.
4. Enable versioning. It is not required for static hosting, but it is cheap
   insurance against an accidental overwrite.
5. Review the settings and choose **Create bucket**.

One thing worth knowing: new buckets are private by default, and AWS now recommends
disabling ACLs entirely. The lab enables them so it can use object ACLs to publish
files. That is an older pattern. I will show a bucket-policy version later that does
not need ACLs at all.

## Understand Block Public Access before you disable it

This is the part people click through without reading. **Block Public Access** is a
set of four account- and bucket-level guards. The lab clears all of them so objects
can be made public, then turns two of them back on at the end.

The order matters:

1. Unblock public access.
2. Make the four objects public with an ACL.
3. Re-enable the blocks for **new** ACLs and **new** public policies.

The site keeps working because those final blocks stop future grants, not existing
ones. If you re-enable them before publishing the objects, every request returns
`403 Forbidden`.

To follow the lab:

1. Open the bucket, go to **Permissions**, and choose **Edit** under
   **Block public access (bucket settings)**.
2. Clear **Block all public access**, save, and type `confirm` when prompted.
3. Upload `index.html`, `hw.css`, `AWS_TE.pdf`, and `expert-logo.jpg`.
4. Select all four objects, open **Actions**, and choose **Make public using ACL**.
5. Return to **Block public access** and re-enable the two options covering new ACLs
   and new public bucket policies.

## The bucket policy from the lab is too broad

The lab also asks you to paste this policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::s3-59676255"
    }
  ]
}
```

It works in the sense that the console accepts it, but I would not ship it:

- `"Principal": "*"` means anonymous users.
- `"Action": "s3:*"` allows every S3 action, not just reads. Anyone could attempt
  writes or deletes if another setting allowed it.
- The resource is the bucket itself. `GetObject` operates on objects, so a policy
  scoped to the bucket ARN does not grant reads on `index.html` anyway. In the lab,
  the public ACLs are what actually serve the files.

If you want a public read-only site through a bucket policy, scope it to the objects
and to `GetObject`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadForStaticSite",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::your-bucket-name/*"
    }
  ]
}
```

Pick one publishing mechanism, not both. If you use this policy, you do not need
public ACLs, and you should leave ACLs disabled at bucket creation. If you use ACLs,
the bucket policy is redundant.

## Add the site files

The lab's `index.html` mixes relative and absolute paths. The stylesheet is loaded
relatively, while the image and PDF point at the bucket's REST endpoint. Relative
paths are more portable, so I would use them throughout:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Hello World!</title>
    <link rel="stylesheet" href="hw.css" />
  </head>
  <body>
    <div class="mainBox">
      <img src="expert-logo.jpg" alt="LODS Expert Challenge Logo" />
      <div class="textBox">
        <h1>Hello World!</h1>
        <p>
          More information about AWS Certification and Training can be found here:
          <a href="AWS_TE.pdf">AWS Certification and Training Overview</a>
        </p>
      </div>
    </div>
  </body>
</html>
```

And the stylesheet:

```css
body {
  background-color: #36a;
}

.mainBox {
  width: 100%;
  display: flex;
  flex-direction: column;
  align-items: center;
}

.textBox {
  width: 30%;
  text-align: center;
}

h1 {
  color: #fff;
}

img {
  width: 50%;
  border: 1px solid #fff;
}
```

Upload the files from the **Objects** tab, then choose **Upload** in the bottom-right
corner. If any uploads fail, re-upload just those files rather than repeating the
whole batch.

## Enable static website hosting

1. Open the bucket and go to **Properties**.
2. Under **Static website hosting**, choose **Edit**.
3. Select **Enable**, then **Host a static website**.
4. Set **Index document** to `index.html`. Add `error.html` if you have one.
5. Save, then open the **Bucket website endpoint** link.

The endpoint looks like:

```text
http://s3-59676255.s3-website.us-east-2.amazonaws.com
```

Note the region in the hostname. This is the website endpoint, not the REST endpoint
(`s3-59676255.s3.us-east-2.amazonaws.com`), and they behave differently. The website
endpoint handles index documents and routing. The REST endpoint is what you use for
API-style object access.

You should now see the logo, the "Hello World!" heading, and a working PDF link.

## Troubleshooting the usual failures

| Symptom | Likely cause |
| --- | --- |
| `403 Forbidden` on the root URL | Public access is still blocked, or the objects were never made public |
| `404 Not Found` | Index document name does not match the uploaded object key |
| Page loads without styles | `hw.css` is missing, misnamed, or the path is wrong |
| PDF link returns `AccessDenied` | That object is private even though the HTML is public |
| Works over HTTP but not HTTPS | S3 website endpoints do not support HTTPS |
| Old content after re-upload | Browser or CDN cache; versioning also keeps the old copy |

## What I would change for production

The lab is a learning exercise, so the shortcuts are fine. For a real site:

- **Skip ACLs.** Keep Object Ownership at *Bucket owner enforced* and publish with a
  scoped bucket policy.
- **Put CloudFront in front of it.** You get HTTPS, a custom domain with ACM, caching,
  and a place to add security headers. Use CloudFront with Origin Access Control and
  the S3 REST endpoint rather than the website endpoint.
- **Add a `Cache-Control` header** to assets and version file names so you can cache
  aggressively without stale deploys.
- **Manage it as code.** A small Terraform or CloudFormation stack is easier to review
  than a list of console steps, and it gives you a repeatable rollback path.
- **Deploy with OIDC.** Let CI assume a short-lived role instead of storing access
  keys.
- **Enable access logging and lifecycle rules** if the bucket will live for a while.

## The takeaway

S3 static hosting is a genuinely useful primitive: cheap, durable, and simple enough
to set up in minutes. The trap is treating the lab's permissive defaults as a
production recipe. Understand what each public-access switch does, scope your policy
to `GetObject` on the objects you mean to publish, and add CloudFront the moment you
need HTTPS or a real domain.

The full flow is short enough to keep in your head:

1. Create a bucket in the right region.
2. Upload `index.html` and its assets.
3. Publish read-only access deliberately.
4. Enable static website hosting.
5. Put a CDN in front before you call it production.

Delete the bucket and its objects when you are done experimenting. A tiny demo costs
almost nothing, but abandoned public buckets are a bad habit to leave running.
